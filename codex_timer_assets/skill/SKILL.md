# Codex Timer

用 shell 调用全局命令 `codex-timer`。任务创建后立即返回，后台进程负责等待。

## 长时间异步任务

用户要求稍后检查或持续跟进训练、批量推理等长时间后台任务时，可根据首次检查安排定时消息，不必要求用户先提供确切时长。仅要求启动任务、没有要求后续跟进时，不自行添加定时检查；用户已给出固定时间和消息时，按其要求执行，不改写消息或另建跟进链。

1. 首次检查实际进程、日志和进度，确认任务正在运行。已经完成或失败时直接处理结果，不再安排检查。
2. 用已有进度估计剩余时长：如 `(总 epoch - 已完成 epoch) × 稳定后的平均每 epoch 耗时`，并考虑验证、保存、排队等耗时。排除启动预热等明显不代表后续速度的样本，简要记录估计依据和不确定性。没有足够进度时安排合理的阶段性检查，不反复轮询来凑一个精确估计。
3. 选择下次值得检查的时间。用户指定的间隔、截止时间或资源预算优先；否则依据预计完成时间或关键阶段安排。不要把估计的结束时间当作实验已完成。
4. 为当前会话创建一条一次性消息，包含实验/作业标识、可定位的日志和结果路径，以及完成、失败、仍在运行时应采取的动作。消息到时应能独立定位任务，不只写无上下文的“check”。用户提供的原文消息仍须原样发送。
5. 先查询当前会话的任务：同一实验已有 `pending` 检查时更新它；保留其他实验或无关提醒。不要为同一次检查创建多条消息，也不要手工重发 `sending` 或 `unknown` 任务。
6. 确认创建/更新成功后报告任务 ID、检查时间和估计依据，然后结束当前回合。等待期间不持续 sleep、轮询或反复汇报无变化的状态。

例：100 个 epoch 已完成 10 个，稳定后约 50 秒/epoch，剩余训练时间约 75 分钟。结合额外耗时和用户期望决定延迟；不是所有任务都用 75 分钟。

```text
codex-timer schedule --after 75m --message "检查实验 exp-a 的进程、runs/exp-a/train.log 和 runs/exp-a/results.json。完成则汇报结果，失败则报告原因；若仍在运行，按用户要求重新估计并设置下一次检查。无实质变化时不反复汇报进度。"
```

示例路径替换为当前项目实际路径。复杂消息可使用下面的 JSON 配置方式，避免 shell 展开。

## 定时复查到达后

读取实际状态和结果；不要因为定时消息到达就宣称完成。只在完成、失败、实质变化或需要用户决策时主动通知，用户要求定期进度报告时按其要求。

任务仍在运行时，只有用户已经要求持续跟进到完成，才根据最新进度再安排一次检查；用户只要求单次检查时不续约。完成、失败或用户要求停止跟进时，不再续约，取消该实验多余的 `pending` 检查。不要取消无关任务。

定时消息只授权其对应检查及用户已授权的后续动作，不扩大到重启训练、修改实验参数或提交其他任务。持续跟进通过每次检查后的单次调度完成，工具本身没有周期调度功能。

## 创建任务

用户提供延迟和消息时直接运行；异步任务按上面的流程推算时间并构造检查消息。普通提醒无法从上下文确定延迟或消息时，只询问缺少的内容。例如：

```text
codex-timer schedule --after 75m --message "请检查实验结果"
```

`--after` 支持 `s`、`m`、`h`、`d`，如 `30s`、`75m`、`2h`。只支持一次性任务。为当前会话设置时省略 `--thread`，工具会读取 `CODEX_THREAD_ID`；不要使用父会话 ID、最近会话或从历史列表猜测目标。

按当前 shell 正确引用消息，使原文不被 shell 展开。复杂的多行内容可以写入临时 JSON 文件，再执行 `codex-timer schedule --config <文件>`，配置字段为 `after` 和 `message`。显式针对另一会话时才使用 `--thread <UUID>`。

确认命令返回成功和 `pending` 状态，再向用户报告任务 ID、发送时间和消息原文。不要通过长时间 sleep 等待，不要把“已创建”说成“已送达”。

## 修改和取消

```text
codex-timer update <任务ID> --after 20m --message "检查最新实验结果"
codex-timer cancel <任务ID>
codex-timer status <任务ID>
codex-timer list
```

只能修改或取消 `pending` 任务；修改延迟会从修改时刻重新计时。用户没有给出任务 ID 时，用 `codex-timer list --thread <当前 CODEX_THREAD_ID>` 查询当前会话的任务并结合请求识别，多个候选且无法判断时再询问。

## runtime 行为及故障

- 目标忙碌：消息立即追加到当前任务；目标空闲：开启新一轮。
- 原 runtime 已关闭或会话已卸载：任务跳过。不要为了发送消息另起 runtime 或恢复历史会话。
- `delivered` 表示 runtime 已接收，不代表消息中的工作已经完成。`unknown` 表示无法确认是否收到，避免自动重发。
- 找不到命令或 runtime 时，用 `codex-timer doctor` 检查。命令安装后新开的终端才能获得更新后的 PATH。
- 普通 CLI 若使用共享 daemon，工具会自动接入已有服务，当前会话无需退出或重新启动。直接调用 `schedule` 即可。
- 桌面应用中也可直接调用 `schedule`，工具通过应用提供的本地消息通道接入当前实例。无需重新启动会话。桌面通道优先于 CLI daemon，接入失败时不会转发到另一服务。
- 桌面端需要当前会话提供的 `CODEX_APP_TOOLS_PIPE_PATH` 和 Node.js（优先使用应用提供的 `CODEX_MCP_NODE_PATH`）；不要从别的会话或历史任务复制通道地址。`threads` 在桌面端只显示当前会话。
- CLI 的 `--no-daemon` 等独立模式无法接入；创建失败时如实说明。不要替换正在运行的 CLI 或为了接入启动其他 runtime。
- CLI 窗口退出后共享 daemon 可能继续运行；只要原 runtime 和会话仍在，任务仍会执行。绑定的 daemon 关闭或替换后跳过，不向新服务转移任务。

若用户要求固定周期任务，说明当前版本只支持一次性，确认是否改为发送一次或按检查结果逐次安排。不要将逐次复查说成已创建周期任务。
